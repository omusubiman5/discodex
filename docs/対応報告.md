# 対応報告: `/connect` の完全リセット化

対応日: 2026-08-29（JST）
状態: 修正・自動test・Pixel実機相互会話を完了

## 実施した修正

`/connect` を「前回状態があれば返す処理」から「前回セッションを完全に切断してから新規接続する処理」へ変更した。

処理順は次のとおり。

1. 前回runnerのcleanup完了を待つ。
2. staleなCodex input routeを復元する。
3. 検証済みruntimeのguild/channelを使い、Discord Voice Stateへ明示的なleaveを送る。
4. 対象と同一Codex taskのGPT Live realtime sessionを停止する。
5. Codex UIがactiveのままなら、一意に特定できるVoice overlayの停止controlだけを操作する。
6. GPT Liveがinactive、不要overlayが閉じたことを確認する。
7. 新しいCodex audio routeをattachする。
8. 新runnerを一つだけ開始する。

いずれかの切断・確認が失敗した場合はfail-closedとし、新runnerを開始しない。

表示するエラーは次へ統一した。

> Connection blocked: the previous Discord/Codex voice session could not be fully disconnected; no new runner was started.

## 主な変更箇所

- `src/adapters/discord/bridge-lifecycle.ts`
  - 非同期cleanupを保持し、`disconnectAndWait()` で完了を待つ。
- `src/adapters/discord/ui-controls.ts`
  - active中の `/connect` でも切断完了を待ってから再接続する。
  - 依存reset失敗を専用エラーへ分離する。
- `src/adapters/discord/production-control-runtime.ts`
  - Discord leave、GPT Live reset、route復元をfresh connectの必須前処理にする。
  - 環境変数ではなく検証済みruntime設定のVoice対象を使う。
- `src/core/codex-app-server-rpc.ts`
  - 対象taskの `thread/realtime/stop`、inactive確認、overlay cleanupを実装する。
  - 日本語の「音声チャットを停止」「音声チャットを終了」の両方を扱う。

## 回帰test

## 結論

今回の原因は `/connect` の依存切断漏れだった。全セッション依存を切断・確認してから再接続するよう修正し、自動testだけでなくWindowsホスト＋Pixelとの相互会話と終了後cleanupまで確認した。今回のWindows/Pixel修正確認について利用者側に追加testを依頼する残作業はないが、macOS実通話E2Eは別の未完了受入項目として残る。
