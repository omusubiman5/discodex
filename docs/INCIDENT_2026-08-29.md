# Discodex Relay接続・再起動インシデント

発生日: 2026-08-28〜2026-08-29（JST）
対象: `codex-discord-voice-bridge` / Discodex Relay
状態: 修正・Pixel実機E2E完了。GitHub上の2026-08-28最終commitへ復元後、原因を分離して再実装

## 概要

Discord `/connect` の失敗を調査する過程で、原因を十分に確定する前に設定とコードを変更した。その後、誤ったDiscord Voice Stateバリデーションを導入し、正式な操作順である「`/connect` 後に利用者がVoice Channelへ参加」を拒否する回帰を発生させた。

最終的にGitHub上の前日最終commitへ復元したが、Discodex Relay GUIを開いたまま外部スクリプトからcontrolを再起動したため、GUIの自動復旧と外部起動が競合した。一方は正常起動し、もう一方は「既に起動中」で終了したが、GUIが非ゼロ終了をタイムアウトと同じ文言へ変換し、`Start Relay exceeded its bounded readiness boundary.` と誤表示した。

## 利用者影響

- `/connect` が複数回失敗し、DiscordとCodex Voiceを接続できなかった。
- 原因と一致しないエラーメッセージが表示され、利用者の復旧判断を妨げた。
- 未接続状態の `/disconnect` が `Interaction rejected.` とだけ表示され、状態を説明しなかった。
- Git復元後、実際にはcontrolがReadyであるにもかかわらず、Relay GUIが起動タイムアウトを表示した。
- 調査と変更の反復により、利用者の信頼を大きく損なった。

確認できた安全面:

- 各失敗時にvoice runnerは残存していない。
- `runtime/live-call.lock` は残存していない。
- Codex input routeは失敗後にrestoreされている。
- stderrおよびsanitized log上、credentialやDiscord IDの露出は確認されていない。

## 根本原因

### 1. 製品journeyを固定せずに局所エラーから修正を開始した

READMEとproject goalにある正規操作順を最初に照合せず、個別のエラー文と一時的なUI状態から原因を推定した。その結果、正規journeyと逆の事前条件を導入した。

### 2. 観測事実と推測を分離しなかった

`404 Unknown Voice State` から確認できるのは「対象guild内に当該Voice Stateがない」ことだけである。それを「別のDiscord通話中」と断定し、事実を超えたメッセージを生成した。

### 3. 単一所有の運用境界を破った

Relay GUIがcontrolを監視・自動復旧している最中に、同じcontrolを外部から停止・起動した。GUI supervisorと外部操作が同じresourceのownerになり、起動競合を発生させた。

### 4. Relay UIが失敗種別を潰している

Relay GUIは子processの `TimedOut=true` と `ExitCode != 0` を同じ分岐で処理し、両方に `exceeded its bounded readiness boundary` を表示する。今回の実態は即時の「既に起動中」であり、タイムアウトではなかった。

## 寄与要因

- task ID変更、Voice判定変更、Discord事前検証を短時間に重ね、変数を一つずつ検証しなかった。
- mock testが新しい誤ポリシーを期待値として固定し、製品journeyとの矛盾を検出しなかった。
- `/connect` 前後の利用者Voice Channel参加順をE2E契約としてテストしていなかった。
- Relay GUIを開いた状態で外部control操作を禁止・調停する仕組みがない。
- start operationが「既に安全なReady状態」を冪等な成功として扱わない。
- GUIが子processの安全な失敗理由を利用者へ伝えず、汎用エラーへ置換する。
- 未接続 `/disconnect` が冪等ではなく、汎用拒否になる。

## 検出できた証拠

- `discord-runner-failed-before-ready:codex-sender-unavailable`
- `discord-runner-failed-before-ready:codex-voice-inactive`
- `HTTP 404 / Discord code 10065 / Unknown Voice State`
- `relay-control-unexpected-exit` と `relay-control-starting` の近接記録
- 競合後も `discord-ui-ready`
- 競合後のcontrol process数は1、runner数は0、lockなし

ログは識別子とsecretを出さない設計のため、本文書にも生のDiscord ID、task ID、credentialを記載しない。

## 封じ込め対応

- GitHubの2026-08-28最終commit `edf0912` へ追跡ファイルを復元した。
- 調査中に追加したコード、テスト、MDを除去した。
- Relay controlを1process、runnerなし、lockなし、`discord-ui-ready` の状態へ戻した。
- 以後、Relay GUI起動中の外部control再起動を停止した。

## 再発防止案

優先度順に、次を別作業として実施する。本文書作成時点では未実装である。

1. 正規journeyをE2E契約として固定する。
   - `/connect` を先に実行できる。
   - その後、利用者が設定済みVoice Channelへ参加できる。
2. Relay GUI起動中は外部start/stopを拒否するか、GUIへ操作を委譲する。
3. startを冪等化する。
   - 既にcontrolが1processでReady、runnerなし、lockなしなら成功として状態更新する。
4. エラー種別を分離する。
   - timeout
   - 子process非ゼロ終了
   - already running
   - Ready readback不成立
5. エラーメッセージは確認済み事実だけを表示する。
6. 未接続 `/disconnect` は `Already disconnected.` とする。
7. task identityをRelay画面で安全に照合できる状態表示を追加する。ただし生IDは表示しない。
8. 一度に変更する原因候補を一つに限定し、各段階で実機結果を確認する。

## 2026-08-29 追補: 最終原因と完了

前日commitへの復元後、現在taskをapp-server `thread/read` では確認できる一方、現行Codex rendererのDOMには従来のtask属性がなく、Voice Talk開始の厳格なDOM照合がfalse negativeになることを確認した。また、別taskの停止済みVoice overlay残留と、初回実機試験でPixelが設定対象外Voice Channelにいたことを分離した。

task照合は、既知のDOM IDが一致する場合、またはDOMにIDが存在せずapp-serverが同一taskのactive・入力可能状態を確認した場合だけ許可するよう修正した。既知の不一致は引き続き拒否する。`task-mismatch` は専用エラーへ分離し、「通話がない」と断定しない。

さらに、Codex出力タップが無音frameを全廃棄していたため往復完了を閉じられない問題を修正し、30frameの有界な無音末尾を転送するようにした。

Pixel 8a実機でVoice Gateway v8、DAVE epoch、UDP受信、DAVE復号、Codex入力、Codex応答、Discord送信を確認し、相互会話2ターンを `turn-roundtrip-completed` として記録した。最終状態はcontrol 1、runner 0、lockなし、入力route復元済み、Pixel通話退出済みである。

## 2026-08-29 追補2: `/connect` の依存切断漏れ

追加調査により、`/connect` は前回runnerの重複防止やinput routeの一部復元は行っていたが、Discord Voice Stateの明示的leaveと、対象Codex taskのGPT Live停止を一つの完了バリアとして実施していなかったことを確認した。したがって、前回セッションが残った状態で新規接続へ進み、後段で別症状のエラーになる余地があった。

`/connect` の前処理へ、検証済みruntime対象へのDiscord leave、対象taskのrealtime stop、Voice overlayのinactive確認・cleanup、stale route復元、非同期runner cleanup待機を追加した。どれか一つでも完了しなければ新runnerを開始しない。

実装後は197件の自動testが全件成功した。さらにPixel実機でDiscord受信、DAVE復号、Codex入力、Codex応答、Discord送信、Pixel再生までの1往復を完了し、終了後はcontrol 1、runner 0、lockなし、route復元済み、Pixel退出済みを確認した。
