# 原因調査: `/connect` の依存切断漏れ

発生日: 2026-08-29（JST）
対象: Discodex Relay / Discord `/connect`
結論: 修正済み、Pixel実機で相互会話まで確認済み

## 現象

`/connect` をやり直しても、前回のDiscord Voice接続、CodexのGPT Live、音声経路などが残ったまま新しい接続処理へ進む可能性があった。その結果、前回状態との競合を後段の「Codex Voiceがない」「runnerを開始できない」といった別のエラーとして表示していた。

## 根本原因

従来の `/connect` は「二重runnerを防ぐこと」と「前回セッションを完全に切断すること」を同じものとして扱っていた。しかし実装されていたのはlock確認、process終了、input routeの一部復元だけであり、次の依存を一つの完了バリアとして切断・確認していなかった。

- Discord Main GatewayのVoice State
- Discord Voice WebSocket、UDP、DAVE epoch/ratchet、SSRC対応、heartbeat/timer
- runner、参加者状態、turn counter、live-call lock
- Codex direct output tapとWebAudio graph
- CABLE input routeとrollback marker
- 接続対象と同一Codex taskのGPT Live realtime session
- 停止済みGPT Live overlay

特にDiscord側はprocessやsocketを閉じるだけでなく、Gateway `Update Voice State` の `channel_id: null` を送ってVoice Stateを明示的に解除する必要がある。Codex側も対象taskのrealtime sessionを停止し、UIがまだactiveなら一意に特定できる停止操作を行い、inactiveを確認する必要がある。

## 誤動作の経路

1. `/connect` を再実行する。
2. lifecycleが既存接続を完全には待たず、またはactive状態を `Already connected` として終了する。
3. Discord Voice StateまたはGPT Live/WebAudioの前回依存が残る。
4. 新しいroute attachやrunner startが古い所有状態と衝突する。
5. 後段の症状だけを元にしたエラーが表示され、実際の「依存切断漏れ」が利用者に伝わらない。

## 寄与要因

- session dependencyの棚卸しと、切断完了条件が仕様化されていなかった。
- `/connect` 再実行のtestが、Discord leaveとGPT Live stopの両方を要求していなかった。
- unit mockではprocess終了を切断完了として扱えてしまった。
- reset処理の初版が、検証済みruntime設定ではなく環境変数だけからVoice対象を読んでいた。
- Codex日本語UIの停止ラベルが「音声チャットを停止」なのに、「終了」だけを照合していた。

後ろ二点は実機検証で発見し、修正と回帰testを追加した。

## 設定・キャッシュの扱い

セッションに属する接続、暗号状態、音声buffer、timer、route、overlay、lockは `/connect` の前に破棄または復元する。一方、credential、許可済みguild/channel、保存済み音量などの永続設定は次回接続にも必要な利用者設定であり、削除対象ではない。永続設定を消すのではなく、前回セッションから派生した状態を残さないことが正しい境界である。

## 検出されなかった理由

従来testは各componentの停止を個別には確認していたが、`/connect` の入口で次の全条件が成立するまで新runnerを開始しない、という統合契約がなかった。

- Discord leave完了
- GPT Live stop完了
- stale route復元完了
- previous runner cleanup完了
- 失敗時は新runnerを開始しない

この契約不足が根本的なtest漏れである。

## 判定

原因は利用者の操作ではなく、`/connect` に必要な前回セッションの完全切断を実装・検証していなかった設計とtestの不足である。Pixel実機での試験は、修正側が負うべき検証として実施した。

## macOS実機試験との関係

2026-08-28にMac実機で次の確認が既に行われていた。

- Apple M4 Pro / macOS 15.5 / Node.js 26.7.0 / ffmpeg 8.1.2
- `npm test` 成功（当時179 passed、macOSでWindows専用4件skip）
- `dist/Discodex Relay.app` の生成と `codesign --verify --deep --strict` 成功
- Relayアプリの起動確認

ただし、BlackHole 2chが未導入で、`runtime/meetron-macos-live.json` も存在しなかったため、`RELAY READY`、Discord↔Codex実通話、macOS E2E証跡検査には到達していない。このため、本修正の相互会話確認はWindowsホスト＋Pixelでの実績であり、macOS実通話での同等確認は未完了である。
